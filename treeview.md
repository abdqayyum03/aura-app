## Reading this tree

- **Backend module shape**: every feature (`devices`, `mqtt`, `sensors`, `alerts`,
  `maintenance`, `notifications`) follows the same `*.controller.ts` / `*.service.ts` /
  `*.module.ts` / `dto/` layout — no separate service layer beyond that, matching the
  size of the project.
- **`*.md` files embedded next to code** (`PAYLOAD_CONTRACT.md`, `ACTUATOR_CONTROL.md`,
  `ALERT_THRESHOLDS.md`, `MAINTENANCE_INTERVALS.md`) are load-bearing, not incidental —
  they document *assumed* values the client hasn't confirmed yet and are referenced
  directly from code comments. Treat "STATUS: PLACEHOLDER" / "STATUS: ASSUMED" in those
  files as still true until someone removes the banner. `PUSH_NOTIFICATIONS.md` is the
  one exception in this family — it documents a feature that's actually confirmed
  working end-to-end, not a placeholder.
- **MQTT is bidirectional now, on two separate connections**: `mqtt-ingestion.service.ts`
  (device→backend, unchanged) and `mqtt-command-publisher.service.ts` (backend→device,
  new) each hold their own MQTT client — see CLAUDE.md for why they aren't shared.
- **Frontend has no backend-shape codegen** — `frontend/src/api/types.ts` and
  `frontend/src/constants/thresholds.ts` are hand-maintained mirrors of backend entities
  and `default-thresholds.ts`. A backend response-shape change requires a manual pass on
  both files; nothing enforces they stay in sync.
